# 12 · Pipeline de CI

> Commit: `ci: enforce coverage threshold, publish coverage report and block secrets in workflows`

La CI existe desde el paso 00 (ADR de Git). Este paso la revisa contra el
checklist del proyecto y cierra los huecos encontrados.

## Workflow `ci.yml` (PR y push a `develop`/`main`)

### Job `quality`

| # | Paso | Detalle |
| - | ---- | ------- |
| 1 | Checkout | `persist-credentials: false` |
| 2 | Node | versión exacta de `.nvmrc`, caché npm |
| 3 | `npm ci --ignore-scripts` | lockfile estricto, sin `postinstall` de terceros |
| 4 | **Política: sin secretos** | falla si algún workflow usa `${{ secrets.* }}` |
| 5 | `lint` | ESLint, 0 warnings, máx. 100 líneas por archivo |
| 6 | `typecheck` | `tsc -b` estricto |
| 7 | **`test:coverage`** | umbral 80 % (líneas, ramas, funciones, sentencias) |
| 8 | Artefacto `coverage` | informe HTML/lcov, 14 días, también si fallan tests |
| 9 | `build` | producción (sin `VITE_SITE_URL` → `noindex`, ver paso 11) |
| 10 | `models:check` | presupuesto del GLB (< 2 MB, < 100k triángulos) |
| 11 | `npm audit --omit=dev` | runtime, nivel *moderate* |
| 12 | **`npm audit` completo** | todo el árbol (incl. tooling), nivel *high* |

### Job `secrets`

gitleaks 8.30.1 (binario oficial, sha256 verificado) sobre **todo el historial**.

## Huecos corregidos en este paso

| Antes | Problema | Ahora |
| ----- | -------- | ----- |
| `npm run test` | El umbral de cobertura **solo se aplicaba en local** | `npm run test:coverage` en CI |
| Sin informe | No había forma de revisar la cobertura de un PR | Artefacto `coverage` |
| Audit solo runtime | Vulnerabilidades graves en tooling (supply-chain de build) pasaban | Segundo audit `high` del árbol completo |
| Sin control | Un secreto en un workflow solo se detectaba revisando a mano | Política automática |

## Sin secretos

Ningún workflow usa `secrets.*`: gitleaks corre como CLI sin token y
release-please usa el `GITHUB_TOKEN` implícito con permisos declarados
(`contents`/`pull-requests: write` solo en ese job). La política del paso 4
impide introducirlos sin una revisión consciente.

## Dependabot (semanal, lunes)

- `npm` → `develop`, máx. 5 PRs, tooling agrupado (minor/patch).
- `github-actions` → `develop` (mantiene los SHA fijados al día).
- Majors ignoradas hasta migración planificada: `eslint`, `@eslint/js`,
  `typescript` (ver paso 00).

## Endurecimiento heredado

Actions fijadas por SHA, `permissions: contents: read` global,
`concurrency` cancela ejecuciones obsoletas, `timeout-minutes` en cada job.

## Verificación

Pipeline simulado en una copia limpia del repo (mismos comandos y orden):
los 8 pasos ejecutables en local, en verde. Los pasos propios de GitHub
(artefacto, política sobre `.github/`) se validan en el primer PR.

## Recomendado (fuera de alcance)

- Ruleset en `develop`/`main` exigiendo `quality` y `secrets` en verde.
- Lighthouse CI con presupuesto (Performance ≥ 90 móvil) cuando haya hosting.
